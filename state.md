# Состояние Codex Connect

Дата: 2026-11-12.

## Результат

Переносимый skill и исполняемый адаптер готовы. Проверены offline suite, независимое ревью и живой обмен итоговым скриптом в разрешённом тестовом диалоге пользователя.

## Архитектура

Один Python-скрипт без сторонних зависимостей. Чтение и адресация через IPC действующего владельца; отправка через bundled codex queue без --resume. Второй app-server, внутренний start-turn, отдельная БД и собственная очередь не нужны.

## Что исправлено после ревью

1. Отправка отклоняется, если проверяемый socket не соответствует выбранному CODEX_HOME.
2. Старый ход из догруженной страницы не подтверждает новую отправку: учитывается время начала queue.
3. Ошибки наблюдения после принятого сообщения сохраняют receipt и запрет повтора.
4. Message-file сохраняет UTF-8 и CRLF без нормализации переводов строк.
5. Некорректные типы статуса/истории возвращают структурированный отказ.

Регрессии дополнительно проверяют неправильного владельца/host/thread, версии и кадры IPC, неоднозначные названия, exact argv, uncertain queue outcome, отсутствие повторной отправки, скрытие reasoning/tool logs и неизвестные backend.

В облачном executor создание AF_UNIX было запрещено sandbox: 12 тестов без socket прошли там, полный набор выполнен в целевом WSL. Это не выдано за неисправность адаптера.

## Граница поддержки

Подтверждён свободный загруженный диалог Linux/WSL. Не подтверждены native Windows named pipe, macOS, незагруженные сессии, отправка во время active/waitingOnUserInput и определение визуального фокуса.

Проверка idle не является атомарной блокировкой ручного ввода в IDE. Внутренний IPC требует контроля версии. Неизвестное время хода или рассинхронизация часов оставляют результат неподтверждённым, а не превращают его в ложный успех.

## Продолжение

Текущий сценарий готов к использованию. Сначала применять его без расширения архитектуры. При обновлении расширения отдельно проверить новый контракт и провести один разрешённый smoke; только затем обновить поддерживаемые версии. Новые состояния отправки добавлять по конкретному запросу пользователя.
