# Состояние Codex Connect

Дата текущей волны: **2026-11-20**.

## Общий UI deadline и диагностика

Отдельный 16-секундный предел PowerShell заменён оставшимся общим бюджетом helper. При `W = --wait` общий deadline остаётся `W + 24`, внешний MSI deadline — `W + 30`. Перед запуском UI вычисляется остаток `R`: при `R <= 3` процесс не запускается; иначе hard timeout равен `R - 1`, внутренний PS deadline — `R - 3`. Read-only observation ограничено `W` и остатком общего бюджета, поэтому медленная навигация может сократить ожидание ответа.

PowerShell проверяет абсолютный UTC deadline и монотонный таймер до UI-действий и после возвращения из них. UIA pattern получается до guard; поздно завершившийся lookup не разрешает новый SetValue или Submit. Превышение UI deadline после dispatch сохраняет `outcome_unknown` и `submit_attempted=null`; автоматического повтора нет. Безопасные коды `UI_PROCESS_TIMEOUT`, `UI_PROCESS_IO_ERROR`, `UI_DEADLINE_EXCEEDED` и поля `inner_ui_timed_out`, `ui_elapsed_ms`, `cause` отделяют внутренний отказ от внешнего MSI timeout. Потерянная диагностика ребёнка не превращается в утверждение, что внутреннего deadline не было.

Историческая диагностика установленной версии: Python probe завершился внутренним TimeoutExpired на прежнем лимите 16 секунд; прямой навигационный PS ProbeOnly успешно открыл точный существующий диалог за **26.245 секунды**, без ввода сообщения и Submit. Это подтверждает недостаточность старого cap, но не является live-приёмкой нового кода.

## Предыдущая волна: завершающий LF в UIA

Сохранены совместимые контракты чтения snapshot 13 и legacy snapshot 11, ограниченные IPC deadlines, сохранение неизвестного pending и переносимый Windows + WSL UI sender с точными UUID/title/cwd, проверкой контекста окна, защитой черновиков и одним адресованным Submit.

Разрешённая живая попытка выявила особенность Windows UIA: `ValuePattern` может опускать один завершающий LF введённого текста. Проверка перед Submit теперь допускает только это единичное различие на границе абзаца, наряду с ранее учтённым добавленным UIA LF. Внутренние строки, пробелы, регистр и обратные слеши остаются значимыми; `Trim()` не используется. Проверка окончания строки использует `StringComparison.Ordinal`.

**Подтверждение доставки по IPC не изменено:** новый полный user turn должен соответствовать исходному тексту после единственной нормализации CRLF→LF. Если история действительно потеряет завершающий LF, исход останется неподтверждённым и повтор запрещён. UIA-сравнение само по себе не является доказательством доставки.

## Что исправлено после ревью

1. Отправка отклоняется, если проверяемый socket не соответствует выбранному CODEX_HOME.
2. Старый ход из догруженной страницы не подтверждает новую отправку: учитывается время начала queue.
3. Ошибки наблюдения после принятого сообщения сохраняют receipt и запрет повтора.
4. Message-file сохраняет UTF-8 и CRLF без нормализации переводов строк.
5. Некорректные типы статуса/истории возвращают структурированный отказ.

Регрессии дополнительно проверяют неправильного владельца/host/thread, версии и кадры IPC, неоднозначные названия, exact argv, uncertain queue outcome, отсутствие повторной отправки, скрытие reasoning/tool logs и неизвестные backend.

В облачном executor создание AF_UNIX было запрещено sandbox: 12 тестов без socket прошли там, полный набор выполнен в целевом WSL. Это не выдано за неисправность адаптера.

## Граница поддержки

Подтверждён свободный загруженный диалог Linux/WSL. Не подтверждены native Windows named pipe, macOS, незагруженные сессии, отправка во время active/waitingOnUserInput и определение визуального фокуса.

Проверка idle не является атомарной блокировкой ручного ввода в IDE. Внутренний IPC требует контроля версии. Неизвестное время хода или рассинхронизация часов оставляют результат неподтверждённым, а не превращают его в ложный успех.

## Продолжение

Текущий сценарий готов к использованию. Сначала применять его без расширения архитектуры. При обновлении расширения отдельно проверить новый контракт и провести один разрешённый smoke; только затем обновить поддерживаемые версии. Новые состояния отправки добавлять по конкретному запросу пользователя.
