# Отправка через Windows UI из WSL

`scripts/send_ui.py` выполняет одну отправку в существующий диалог Codex.
Python читает состояние через соседний `codex_connect.py`; PowerShell работает
только с обычным интерфейсом VS Code через Windows UI Automation. Скрипты не
запускают второй backend, не создают диалог и не записывают сообщения в БД.

## Проверенная граница

Структура интерфейса сверена с Windows VS Code и расширением
`openai.chatgpt 26.1111.21308`, bundled CLI `0.169.0-alpha.11.1`, snapshot
protocol **13**. Проверка UI требует `observation.snapshot_version == 13`;
совместимость чтения с protocol 11 не разрешает этот UI-маршрут для старого
интерфейса. Legacy native queue описан отдельно в [protocol.md](protocol.md).
Проверка snapshot-версии не устанавливает версию самой UI-сборки: при обновлении
расширения с прежним номером протокола селекторы и один разрешённый smoke нужно
проверить заново.

Поддерживается Python 3.10+ внутри того же WSL-дистрибутива, с тем же Linux
пользователем и стандартным `~/.codex`, который использует расширение. Значение
`WSL_DISTRO_NAME` должно быть известно и точно совпадать с контекстом окна.
Пользовательский `CODEX_HOME` и неизвестная привязка профиля UI не поддерживаются.
Для другого профиля нельзя передать стандартный путь только ради обхода отказа.

Селекторы привязаны к наблюдаемым английским UIA-именам: `Back`, `Chats`,
`Recent chats.`, `Send`, `Stop`, `Ask for follow-up changes`, а также
`status.host` и `recent-tasks-search`. Другая локализация, VS Code Insiders,
native Windows backend, SSH/Dev Container и macOS не подтверждены. Неизвестный
контекст или изменившиеся элементы приводят к отказу, а не к поиску похожего окна.

Windows PowerShell должен быть доступен через WSL interop и разрешать запуск
локального `.ps1` согласно текущей политике выполнения. Helper не изменяет эту
политику и не добавляет `ExecutionPolicy Bypass`. Скрипт и временный файл
передаются через `wslpath -w`; Windows должен иметь доступ к этому WSL-пути.
Ни имя пользователя Windows, ни диск, ни каталог установки не зашиты в код.

## Вызов и ограничения

Из корня checkout посмотреть полный интерфейс:

```bash
python3 skills/codex-connect/scripts/send_ui.py --help
```

Для реальной операции вызывающий агент передаёт аргументы массивом без shell
интерпретации. Все значения адресата нужно брать из чтения выбранного диалога.

| Аргумент | Значение |
| --- | --- |
| `--thread` | Полный UUID существующего диалога |
| `--title` | Точное название, уникальное в БД выбранного `CODEX_HOME` |
| `--expect-cwd` | Точный cwd этого же диалога |
| `--message-file` | Обычный файл UTF-8, без symlink, до 32768 байт, без NUL |
| `--wait` | Ожидание подтверждения в live IPC: от 0 до 60 секунд, по умолчанию 15 |
| `--probe` | Проверить доступность UI; текст сообщения не вводится и не отправляется |
| `--codex-home` | `CODEX_HOME` или стандартный `~/.codex`; нестандартный путь отклоняется |
| `--adapter`, `--ui-script` | Явные пути к доверенным локальным частям пакета; по умолчанию соседние файлы |
| `--powershell` | Путь к Windows PowerShell; иначе `CODEX_CONNECT_POWERSHELL` или `powershell.exe` из PATH |
| `--wsl-distro` | Дополнительная проверка: должен равняться текущему `WSL_DISTRO_NAME` |

`--probe` всё равно требует валидного message-file и полной проверки адресата.
Он может восстановить свёрнутое окно, открыть список существующих чатов,
заполнить поле поиска точным названием и переключить видимый диалог. Он не
вводит текст в composer и не вызывает Send. Это не полностью пассивное чтение.

## Проверки перед вводом

Python разрешает UUID и точное название через одну и ту же локальную БД. Обе
записи должны указывать на тот же UUID и cwd. Неоднозначное название блокирует
операцию, даже если один из диалогов открыт. Live IPC обязан подтвердить тот же
адресат, idle, известное отсутствие pending requests и отсутствие
неподтверждённых отправок.

PowerShell перечисляет **все верхнеуровневые окна Code**, включая несколько
HWND одного процесса. WSL-контекст проверяется по UIA `status.host`, а не по
сходству заголовка. Если несколько окон соответствуют дистрибутиву, допускается
только единственное окно с уже видимым точным целевым документом. При отсутствии
такого доказательства выбор неоднозначен. Ошибка содержит не более восьми
кандидатов: HWND, PID и признаки контекста, без заголовков и домашних путей.

Навигация использует существующий чат с точным названием. После выбора
проверяется документ этого чата, composer и Send. Перед staging и непосредственно
перед единственным вызовом Send проверки окна, WSL-контекста, документа и текста
повторяются с новыми UIA-объектами. Используются адресованные ValuePattern,
InvokePattern и связанные UIA-действия; клавиатурные события и clipboard не
используются, поэтому ввода в другое активное приложение нет.

Непустой черновик не заменяется. Пустой composer и текст подсказки различаются
с учётом доступности Send: активный Send означает потенциальный черновик или
вложения и блокирует staging. После staging ошибка оставляет текст на месте;
helper не пытается его очистить. Ручные действия пользователя не участвуют в
блокировке, поэтому полностью атомарной гарантии относительно одновременного
редактирования в IDE нет.

Один кооперативный Linux-lock защищает ввод текущего пользователя. Дополнительно
Windows mutex с SID пользователя сериализует UI-ввод разных WSL-конфигураций
одного desktop-сеанса. Ожидание mutex неблокирующее. При abandoned mutex текущий
вызов отказывается от отправки; освобождается только захваченный mutex.
Блокировки снимаются после работы с UI, до ожидания ответа через IPC.

## Результат и восстановление

Вывод — один JSON-объект. Exit code 0 означает `observed` или успешный `ui_ready`;
2 — установленный отказ до submit; 3 — неопределённый исход. Всегда читать
`phase`, `outcome`, `submit_attempted` и `last_confirmed_phase`, а не один exit code.

| phase | Что установлено |
| --- | --- |
| `failed_before_send` | Submit не вызывался; `outcome=not_sent`, `submit_attempted=false` |
| `ui_ready` | Успешный probe, без ввода сообщения |
| `staged_not_submitted` | Submit не вызывался; после staging мог остаться черновик |
| `ui_invoked` | UIA-вызов Send выполнен; доставка ещё не подтверждена |
| `ui_invoked_unobserved` | За отведённое время надёжное подтверждение не получено |
| `outcome_unknown` | Неопределённость после запуска UI-процесса или неоднозначное наблюдение |
| `observed` | Найден единственный новый полный user turn с точным текстом и допустимым временем |

Корреляция исключает baseline turn IDs и исторические страницы. Время начала
нового хода обязано быть не раньше фактического начала submit. Отсутствующее
время, несколько совпадений, усечённый текст или рассинхронизация часов не
подтверждают доставку. При сравнении переписки нормализуются только CRLF в LF:
пробелы, завершающие строки и обратные слеши сохраняются. Во время чтения самого
composer допускается ещё один завершающий LF, который UIA добавляет к
contenteditable; эта уступка не используется при подтверждении доставки по IPC.

Тайм-аут, повреждённый JSON и отсутствие полного результата после запуска
PowerShell считаются неизвестным исходом. Повторной UI-отправки в helper нет.
`observed` подтверждает пользовательский ход, а не завершённый ответ модели;
отдельное поле `reply_observed` сообщает, виден ли уже текст ассистента.

Сам helper не создаёт долговечный журнал операций. Вызывающий мост обязан
сохранить `operation_id` **до запуска helper** и привязать к нему исходный
адресат, хеш сообщения, baseline и результат. После обрыва связи нужно читать
исходную квитанцию и live-историю. `retry_safe` всегда false: даже установленный
отказ может оставлять staged draft или требовать устранения причины вручную.

## Проверка

```bash
python3 -m unittest discover -s tests -p test_send_ui.py -v
python3 -m py_compile skills/codex-connect/scripts/send_ui.py
```

Windows fixture запускается в PowerShell из корня checkout:

```powershell
& ./tests/test_send_ui_windows.ps1
```

Python-тесты используют синтетическую БД и fake subprocess. Windows fixture
загружает только определения функций и проверяет тот же выбор окна и guards
черновика на синтетических данных. Он не перечисляет реальные окна, не загружает
UIAutomation и не вводит текст. Эти проверки не доказывают работу реального
ValuePattern/InvokePattern, навигации, WSL interop и доставки в установленной
сборке. Фактически выполненные live-проверки и оставшиеся ограничения фиксируются
в [state.md](../../../state.md); перед включением новой сборки требуется один
разрешённый пользователем smoke в выделенном диалоге.
