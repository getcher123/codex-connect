# Remote Desktop Commander и WSL

## Найти среду

1. Найти инструменты Remote Desktop Commander и получить список устройств. Использовать возвращённый deviceId; не переносить его из другой среды.
2. Проверить окно VS Code и список WSL-дистрибутивов командой `wsl --list --quiet`.
3. В выбранном дистрибутиве проверить процессы и запустить адаптер. Облачный Linux, Windows host и WSL имеют разные файловые системы и sockets.
4. Использовать установленный skill или передать скрипт файловым инструментом во временный каталог пользователя. Не подменять файлы расширения и не изменять CODEX_HOME.
5. Выполнить doctor для новой среды, затем discover/status/read; отправку выполнять только по запросу пользователя. Read/status не должны повторно запускать CLI version probe.

Проверенная установка работала через WSL. На другой машине всё равно проверить фактическую среду. Для UI прочитать [windows-ui.md](windows-ui.md): учитывать все верхнеуровневые окна Code, а не только Process.MainWindowHandle. Один процесс может иметь Windows- и WSL-окно одновременно.

## Передать текст

Предпочесть UTF-8 message file и --message-file. Для subprocess использовать массив argv. Не вставлять содержимое сообщения в PowerShell/Bash конкатенацией: кавычки и подстановки должны остаться текстом.

Большой скрипт передавать файловым инструментом, а не длинной командной строкой Windows. Временные файлы изолировать и удалять после проверки. Не сохранять вместе с ними переписку, токены или config.

## Дождаться процесса

Если start_process вернул PID, читать read_process_output. Если инструмент вернул running call_id, использовать get_tool_result именно с ним.

PID или timeout не являются основанием повторить send. Сначала установить исход процесса, затем прочитать сессию. Короткий --wait позволяет регулярно сообщать статус; долгую задачу наблюдать последующими read.

## MSI Remote Agent

Использовать совместимые bridge, IPC adapter и UI sender вместе. До первого вызова контроллер сохраняет operation_id и передаёт его в codex_send_message. Квитанция должна появиться до первого preflight-чтения. После неопределённого ответа читать codex_delivery_status по исходному ID.

`refresh=false` читает квитанцию без IPC; обычный poll при занятой блокировке возвращает сохранённый этап; `refresh=true` явно сверяет неизвестный исход. `not_found` не доказывает отсутствие отправки. Блокировки и повреждённые квитанции не удалять автоматически.

Туннель, MCP handshake, IPC snapshot и доставка — разные слои. Здоровый туннель не доказывает работу остальных. Внешнюю ошибку инициализации, включая 409, описывать с указанием слоя; неизвестный исход мутации не исправлять replay.

Новый код проверять в отдельном каталоге. Полный synthetic suite и read-only live snapshot не заменяют разрешённый тест Submit. Работающий пакет обновлять отдельным согласованным развёртыванием.

## Если подключение не удалось

- Нет устройства: сообщить о недоступности.
- Нет socket: проверить пользователя, дистрибутив и запущенное расширение.
- Нет owner: открыть существующий диалог в IDE, не запускать второй сервер.
- Несколько backend: выбрать проверенный экземпляр явно.
- Неизвестная версия: обновить контракт после проверки, не отключать контроль совместимости.

Чтение auth.json и перенос токенов для этих действий не требуются.
